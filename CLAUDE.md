# Claude Code — Archivey

**Read [`AGENTS.md`](AGENTS.md) first.** It is the canonical agent guide: repo map,
session setup, the OpenSpec CLI, the `archivey-dev` reference repo, the 7z/RAR
native-first strategy, and the conventions. `CONTRIBUTING.md` holds the coding and
testing standards, including the "Before pushing…" three-config rule.

This file exists because Claude Code auto-loads it by name. It carries only what is
specific to Claude Code; everything else would drift if it were duplicated here.

## Claude Code specifics

- **Session setup runs automatically** via the `SessionStart` hook
  (`.claude/hooks/session-start.sh`, registered in `.claude/settings.json`). It calls
  the same `scripts/setup-dev-env.sh` every other environment uses, so they cannot
  drift, and it no-ops unless `CLAUDE_CODE_REMOTE=true` — a developer's own machine is
  left alone.
- **Read the hook's closing verification block.** `unrar` and `7z` missing makes about a
  hundred tests *skip quietly* while the suite still reports green. The script names anything
  missing on its last lines; if you did not see them, run it by hand.
- **The `openspec` CLI installs to `~/.local/bin`** here, because the global npm prefix
  is not user-writable. `AGENTS.md` §OpenSpec CLI leads with the
  `--prefix "$HOME/.local"` recipe that works on this image.
- **`archivey-dev` is not in the GitHub-tool scope** of a Claude Code session. Plain
  HTTPS `git clone` works; the GitHub API returns 403 for unauthenticated calls, which
  is rate limiting rather than a private repo. See `AGENTS.md` §Reference repository.
- **A fresh container has no memory of earlier sessions.** Transcripts do not survive; the
  durable record is the repo plus the PR history. Before re-deriving something that feels
  like it should already be settled, check `dev-docs/code-map.md` §"Where the answers
  live" — ADRs, `dev-docs/design-rules.md`, `review/STATUS.md`, `dev-docs/discussions/`,
  and the threat model exist precisely so questions get answered once.
- **Skills for the review loop:** `/code-review-skill` produces findings, `/address-
  review-findings` dispositions them. Ask for those two by those names — a bare `/code-
  review` is a *builtin* skill, not this repo's. A Linear ticket goes through
  `.claude/skills/address-linear-issue/SKILL.md`, which sequences them: implement, open
  the PR and add the `review` label; the [review loop](dev-docs/review-loop.md) runs
  `code-review-skill` in a separate session; then address. Do not spawn a reviewer of
  your own. The autopilot entry point is a **path, not a slash command**: if you are
  reacting to PR events rather than being asked, read `.claude/skills/steward/SKILL.md`,
  which routes to `address-review-findings` and carries this repo's autonomy boundary.
  `AGENTS.md` §Review workflow has the handoff, including why agent-authored PR comments
  must be identifiable as such: in a Claude Code session, end every comment and review
  you post with the `_Generated by [Claude Code](https://claude.ai/code)_` footer,
  written yourself.
